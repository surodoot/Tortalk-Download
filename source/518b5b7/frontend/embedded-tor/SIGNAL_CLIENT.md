# Signal client integration: bounded one-to-one pilot

`SignalClient` uses official `org.signal:libsignal-client:0.105.0` protocol classes and native code. Android additionally uses official `libsignal-android:0.105.0`. The dependency repository is restricted to the `org.signal` group. The actual resolved client JAR and Android AAR are SHA-256 checked before building; the pins also appear in `scripts/signal-artifacts.sha256`. Pinning establishes the reviewed bytes, not an independent audit or reproducible-build proof. Libsignal is AGPL-3.0; distribution must preserve its applicable licensing/source obligations. The AAR's packaged acknowledgments remain included.

## Implemented boundary

- Every installation independently generates its identity pair, registration ID, protocol device ID, signed EC prekey, and one-time EC/Kyber-1024 pairs using libsignal. No shared fixture identity, custom key agreement, or fallback cipher.
- The backend device public key is the raw 32-byte identity public key. Libsignal bundles transport its typed `05 + 32` serialization. `SignalJson` verifies the SHA-256 device digest against that exact raw key.
- A contact identity and protocol/device/account binding must be explicitly accepted with `acceptPeer` after the UI's contact/fingerprint/QR confirmation. Merely downloading a bundle does not pin an identity. Identity or device changes are rejected during normal session setup. Only `replacePeerIdentity`, invoked after a separate explicit old/new fingerprint confirmation, can replace a stored peer binding. It checks the exact expected old pin and atomically clears that peer’s old sessions/room bindings while retaining history. A QR or fingerprint is only authentic if users compare it over a trustworthy channel.
- `acceptBundle` checks the pinned identity/protocol, validates both signed-prekey signatures through official libsignal public-key methods, and creates the session through official `SessionBuilder`. An active session is not reset by retrying a claim.
- Text validation strictly encodes UTF-8 with malformed-input reporting. It rejects unpaired UTF-16 surrogates and values above 4,096 UTF-8 bytes before state changes, while preserving Korean, emoji, combining characters, line endings and whitespace exactly. The pure `SignalClient.checkText` validator is available to native UI input validation.
- `stageText` encrypts an inner versioned frame containing exact room, message, sender account/device, recipient account/device and UTF-8 text. Ciphertext and ratchet update are committed together before returning the outbound envelope. Exact retries return the originally committed bytes.
- `receive` verifies outer recipient/contact binding, decrypts, validates every authenticated inner field, and atomically commits the ratchet, one-time-key consumption and durable inbox/dedupe record before returning permission to ACK. Failed verification or storage does not release plaintext or advance durable state. Replayed identical envelopes return a duplicate result; changed bytes under the same ID fail.
- The relay wire body is one libsignal type byte followed by serialized ciphertext, base64 encoded, under suite `signal-pq-v1`. Unsupported message types fail closed. `SignalJson` separately checks relay receipt context, version, suite and pinned key digests.
- Claim IDs, message IDs/ciphertexts, device credentials and pending refill batches survive process restarts. `pendingReplenishment` reads a previously prepared batch without generating keys, allowing an accepted-but-unacknowledged batch to be retried even if the server pool is already full. Refill keys are freshly generated, monotonically numbered, signed and stored before publication. HTTP retries reuse the persisted batch; the caller confirms it only after server acceptance.
- Device credentials are generated and saved before registration. Their scope is the persisted onion origin/account/device. Conversation state has no implicit reset or account/origin migration.

## Storage and concurrency contract

The production `StateStorage` adapter must encrypt all bytes with the Android Keystore-backed `KeystoreBlobStore` per-origin/account Signal namespace. The coordinator derives separate aliases and authenticated file bindings for separate profiles; it never rebinds an existing `SignalClient` profile. No plaintext key/state database is written by `SignalClient`. The adapter must implement `compareAndSave(expected, next)` with the store's locked write validator, rejecting stale state while holding the same lock through atomic replacement. The callback's success must mean encrypted data and its atomic replacement are durable. The coordinator also serializes operations and owns a shared client. A disk/key/decryption error must block work, not cause a new identity to be silently generated.

The Android adapter's reviewed durability sequence explicitly synchronizes the encrypted file before `AtomicFile.finishWrite`, marks the commit as attempted before entering that API, verifies the resulting encrypted bytes, and synchronizes the parent directory. An exception after a commit attempt preserves the uncertain file; it does not roll back, clear, or generate replacement state. Recovered reads synchronize both file data and the directory before key lookup/decryption can release persisted ratchet/outbox bytes. Directory descriptors are opened without following symlinks, checked as directories, synchronized and closed with errors propagated. The source guard includes negative mutations for removal/reordering of these barriers and for unsafe post-commit rollback.

The storage host harness executes production code against explicit Android/Keystore/filesystem doubles. Its injected failures test ordering and fail-closed control flow, including replacement followed by an exception and file/directory synchronization failure. This is not a physical power-loss or Android filesystem durability claim; actual device execution remains required.

The default `compareAndSave` exists for simple single-owner test stores. It is not a replacement for the production adapter's atomic file-locked comparison across separate storage instances.

Ciphertext, plaintext history and private key material remain in process memory during operations. Disk encryption does not protect an unlocked compromised process or rooted device. JVM test fixture files are explicitly plaintext synthetic state in a disposable mode-0700 directory and are never the Android storage implementation.

## Bounds and remaining gates

This pilot supports one active device per account, one-to-one text, at most 4,096 UTF-8 bytes per message, batches of at most 20 prekey pairs, and a bounded 16 MiB/12,000-record encrypted state. New local profiles exclude known historical protocol device IDs before generating their immutable identity. Explicit peer replacement retires old outbox ciphertext: it remains in history with `retired=true`, is removed from the retry queue, and cannot be relabeled or emitted under the new pin. The current store retains history and dedupe records; hitting a bound rejects additional writes. Automatic key/identity rotation, private-key/device-state migration, multi-device fanout, group messaging, media, delivery/read receipts and a production history/retention policy are outside this bridge. Relay acceptance is not delivery or a read receipt. Prekey exhaustion is surfaced and refill requires server-confirmed capacity.

The host fixture tests do not establish Android native loading, Android Keystore crash durability, Gradle/D8 packaging, real Tor networking, screenshots, or two-device end-to-end app operation. These gates still require their actual environment. Neither this bridge nor a JVM/HTTP pass establishes anonymity or audited production security.

### Separate process and public-contact follow-up

The reviewed source guard additionally requires the app-private `:tor` service, initially disabled networking, exact owner/UID/epoch/sequence IPC, sender-time leases, an independent watchdog and termination limited to the verified current Tor PID. Native Binder death revokes the immutable readiness epoch before UI cleanup. Only exact Binder death confirms termination; elapsed time, unbinding and control shutdown requests do not. The main application and both Activities must retain their main process so the remote self-termination path cannot target the UI. Host mutation checks are not evidence of an actual Android process kill.

Public contact QR support uses only checksum-pinned `com.google.zxing:core:3.5.4` and retains the complete upstream `zxing-LICENSE.txt`. The six-field card carries public origin/account/device/protocol/identity data. The native transient content picker and bounded PNG/JPEG importer do not expand WebView file or network access; imported identity data must match the captured current peer and still requires explicit confirmation. The content provider is outside the app transport boundary; its own I/O is not claimed to use Tor. See [contact codec provenance and tests](CONTACT_QR.md) and [native process limits](docs/native-tor-process-boundary.md).

### Read-only local archive

Server room listings may omit closed or blocked conversations. `SignalClient.listLocalRooms(expectedOrigin, expectedAccount, peerFilter, afterRoomId, limit)` derives the local listing from one encrypted state snapshot: explicitly verified room bindings and durable sent/received message contexts. It never imports a room association from UI or server display fields. Empty `peerFilter` explicitly lists all verified rooms in the bound profile; a nonempty filter selects one account. Limits are 1–40 rooms, ordered by room ID. Empty cursors start and terminate pagination; null inputs are invalid. A missing state returns an empty listing without generating keys.

`openLocalRoom(expectedOrigin, expectedAccount, roomId, expectedPeer, beforeMessageCursor, limit)` requires the exact local association and accepts page limits of 1–200 messages, oldest first within each returned page. Empty verified rooms return an empty page. Empty cursor selects the latest page; the returned opaque cursor anchors the next older page inside the same room. Selection retains at most one extra record beyond the page limit; the underlying state remains bounded to 16 MiB and 12,000 records. Profile mismatch, conflicting historical/current peer bindings, or a cursor from another room fails closed. Old-identity history remains readable after its current session and room pin were retired, because its original authenticated message context remains durable.

These reads never commit state, initialize identities, deserialize session records, claim prekeys, encrypt/decrypt new messages or authorize an ACK. The native history DTO retains existing encrypted message envelopes for internal validation. Its JSON projection exposes only local associations/text/status; private keys and ciphertext are never projected into the UI. Existing ciphertext, timestamps, Unicode plaintext and accepted/retired status stay unchanged. Earlier live transactions already executing may finish their previously authorized durable commit before the serialized archive read; archive selection suppresses their obsolete network/callback continuation and does not roll back those commits.

`MessageCoordinator.listLocalRooms(peerFilter, afterRoomId, limit, LocalRoomsCallback)` returns `{rooms:[{room_id,peer_id,message_count,last_message_at,read_only:true}],next_after}`. `openLocalRoom(room, expectedPeer, Callback)` opens the latest 200 messages; its overload accepts `beforeMessageCursor, limit` before the callback. `currentRoom()` and `messagesForRoom()` expose the bounded view; `isLocalArchive(room)` and `localArchiveNextBefore()` identify its mode and older-page cursor. Origin/account/profile identity and operation generation are captured before work and checked again before delivery. Obsolete callbacks and profile switches cannot expose old history.

Archive selection cancels current live work, clears the live peer/readiness view, and immediately rejects enrollment, live-room opening, key verification/replacement, maintenance, send, retry and poll operations with `LOCAL_ARCHIVE_READ_ONLY`. `isReady()` remains false. No server request is issued by archive listing or opening, and no old room is reopened or ciphertext retargeted. The UI must explicitly call `leaveLocalArchive()` to return to a live flow; that method itself does not restore readiness or send anything. The host JNI and coordinator suites exercise these properties. Prepared Android archive checks still require the separately authorized disposable-device runtime run.
